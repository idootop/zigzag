# 基准测试

ZigZag 对外说的每一个数字都出自这里。这份文档记的是**怎么测的**和**测出了什么**，
脚本就在本目录下，可以自己跑一遍复现。

设计文档、决议记录（ADR）与完整开发日志在 [PROGRESS.md](../PROGRESS.md)。

## 快速开始

```bash
pnpm bench:verify    # 校验语料与清单一致（换机器/换时间先跑这个）
pnpm bench:size      # 体积轴：直接读库出分 kind 压缩率
pnpm bench:image     # 质量轴 · 图片：SSIMULACRA2
pnpm bench:video     # 质量轴 · 视频：VMAF 三窗抽样
pnpm bench:sample    # 耗时轴：内存 / CPU 采样（开跑前起它，跑完 Ctrl-C 打小结）
pnpm bench:100k      # 规模压测：用 APFS clonefile 十几秒造十万个文件
```

| 依赖 | 用途 | 装法 |
|---|---|---|
| ffmpeg / ffprobe sidecar | VMAF、参考解码、缩放 | `pnpm sidecars` |
| `ssimulacra2` | 图片质量 | `brew install ssimulacra2` |
| `pyobjc-framework-Quartz` | ImageIO 参考解码 | `pip install pyobjc-framework-Quartz` |
| `b3sum` | 语料哈希校验（可选，缺了只校验大小） | `brew install b3sum` |

质量与体积脚本都从**应用自己的库**里读源与产物的对应关系（默认
`~/Library/Application Support/com.zigzag.app/zigzag.db`，可用 `ZIGZAG_DB=` 换成别的），
所以得先用应用跑一遍，再跑这些脚本。

## 一条硬规矩：跑打包好的 `.app`，不许用手搓的 ffmpeg 命令代替

这是发布前验收基准（基准 22）和之前 21 个基准的本质区别。

前 21 个基准拿裸 ffmpeg 测单点参数，回答的是「**参数选得对不对**」。而调度、短边规则、
无收益跳过、元数据保留、完整性校验、原子提交、断点续传这些事**只在完整管线里才发生**，
单点参数基准一个都覆盖不到——所以验收基准跑的必须是 `bundle/macos/ZigZag.app`，
默认档，一次不改参数。

## 语料

`bench/b8/`，**31 个文件 / 111.8 MB**。素材本身不进 git，进 git 的是
`bench/manifest-8.tsv`——「相对路径 + 大小 + BLAKE3」的清单，用 `pnpm bench:verify` 校验。

**这份语料是按「格式覆盖」定的，不是按「数量规模」定的**（D-160）。每一个文件都对着
一条会分岔的处理路径：

| 样本 | 它验的那条路 |
|---|---|
| `screenshot/tall.png` 750×30000 | 短边规则的边界——短边已低于上限，一个像素都不该动 |
| `camera/android.jpg` 6528×3680 | 常规缩放 |
| `phone/rot.jpg` 3024×4032（竖） | EXIF 朝向烘焙进像素 |
| `camera/cmyk.jpg` | Adobe 反相 CMYK JPEG（APP14 + `transform=0` + 无 ICC） |
| `phone/p3.jpg` | Display P3 色彩空间保留 |
| `phone/*.heic` | HEIC 解码（走 ImageIO 兜底） |
| `anim/*.gif` `.png` `.webp` | 动图 → 动画 AVIF；含单帧 GIF、变延迟 GIF、带 ICC 的 |
| `video/screen.mov` | 屏录，同时触发缩放 + 帧率上限 |
| `audio/music.aac` | **已是 AAC 的源**——验只换容器不重编 |
| 9 个小文件 | 低于 `min_file_kb` 的跳过路径 |
| `other/a.tif` `a.bmp` | 按 D-60 不算媒体，扫描阶段就该忽略 |

**代价必须说清楚**：31 个文件里视频占了 75% 的字节，而真实归档盘上照片才是主力，
所以**整体压缩率不是一个有代表性的加权平均**——分 kind 的那三个数才是可以对外说的。
另一个盲区是语料里没有「已经压实了的 AVIF/WebP」，因此 `no_gain` 跳过一次都没触发，
而那在真实归档盘上是常态路径。

## 三轴方法

### 体积 — `pnpm bench:size`

直接读库（`status='done'`），逐文件都有记录，不靠 `du` 估。按 `kind` 分组。

> 库是 WAL 模式，**不要 `cp` 一份 `.db` 出来查**——最近的写还在 `-wal` 里，
> 拷主库等于读了一份过期快照。脚本是只读连原库的。

### 质量 · 图片 — `pnpm bench:image`

SSIMULACRA2。约定：90 ≈ 视觉无损，70 ≈ 高质量，50 ≈ 中等。三条口径都是实测钉下来的：

1. **参考端先缩到产物尺寸再比**。指标要求两张图尺寸相同，而管线是「先缩放后编码」。
   缩放用 ffmpeg `scale=W:H:flags=lanczos`——实测只有 lanczos 能复现记录在案的分数
   （`android.jpg`：lanczos **84.76** / bicubic 85.12 / bilinear 85.41 / spline 84.94）。
   所以这里量的是**编码损失**，缩放那一半的损失不在分内。
2. **参考解码器默认 ImageIO**（`decode-imageio.py`），因为应用自己的解码兜底走的就是它
   （D-14）——拿它当参考才是在量「用户会看到的差别」。
3. **只有 ImageIO 明确解错时才换 ffmpeg，且换就两端一起换**（输出里标 ※）。见下方「量错过的地方」。

### 质量 · 视频 — `pnpm bench:video`

VMAF。口径与 `src-tauri/src/engines/vmaf.rs` **逐项对齐**，差一项分数就不一样：

- 三窗 15% / 50% / 85%，每窗 2 秒（全量打分的耗时与编码同一量级，不现实）；
- `-ss` 前置（真 seek），两路都套 `setpts=PTS-STARTPTS` 归零——libvmaf 靠 framesync
  **按时间戳配对**两路帧，而产物与源的 time_base 不同，不归零会配错；
- 参考端套上编码时那条 `-vf`（缩放 + 帧率上限）。脚本按源与产物的实际规格自动推导，
  规则同 `engines/video.rs` 的 `filters()`；
- libvmaf 入参顺序是 `[dist][ref]`，反了分数会变。

### 质量 · 音频

不做客观质量分：可用的客观指标（ViSQOL / PEAQ）引入成本远超收益，而默认档
128k AAC-LC 的参数正确性在基准 2（ADR-003）已经验过。这里只验「管线有没有把参数正确用上」：

- **AAC 源确认走 copy 不重编**——两边抽出 ADTS 裸流比 MD5。
  > 差点误判：对整个文件做 `-f md5` 得到两个不同哈希，看起来像重编了。那个哈希算的是
  > **容器字节**，remux 必然不同。要验「有没有重编」得比**裸流**。
- **采样率继承、目标码率生效**——`ffprobe` 逐个核对。

### 耗时与内存 — `pnpm bench:sample`

墙钟、CPU 时间、并行加速比、内存曲线。两条量法上的硬规矩：

1. **内存一律用 `phys_footprint`，`ps -o rss` 作废**（D-156）。
2. **峰值读 `phys_footprint_peak`，轮询只用来看曲线形状**。

理由在下方「量错过的地方」。

## 结果 · 基准 22（发布前验收，2026-08-09）

跑打包好的 `.app`、默认档、镜像模式，**完整跑两遍**（第二遍换独立库、换输出目录，
一遍量数、一遍验确定性）。

### 体积

| kind | 个数 | 源 | 产物 | 占原体积 |
|---|---|---|---|---|
| image | 13 | 11,785,213 | 1,689,714 | **14.3%** |
| audio | 3 | 17,185,925 | 2,455,481 | **14.3%** |
| video | 4 | 80,246,828 | 17,052,721 | **21.3%** |
| **合计** | **20** | **109,217,966** | **21,197,916** | **19.4%** |

账要对得上：**31 = 20 处理 + 9 跳过（全是 `too_small`，合计 193 KB）+ 2 个不算媒体**
（`a.tif` / `a.bmp` 按 D-60 移出支持范围，扫描阶段就当非媒体忽略，连条目都不建）。

几个值得单看的：`screen.mov` 44.3 MB → 2.5 MB（**5.6%**，屏录素材 x265 最吃得开）；
`cam720.mp4` 69.1% 与 `ui720.mp4` 60.7% 是两个**压不太动**的样本（源码率本来就不高），
它们没触发无收益跳过，说明那道闸门的阈值定得不算激进。

**扫描阶段的预估对得上**：报告给的是 21.9 MB 产物 / 省 87.4 MB（区间 68.1~94.1 MB），
实测 21.2 MB / 省 88.0 MB，落在区间内、略偏上——预估模型不需要重标。

### 短边规则（逐张读产物真实像素核对，不是看文件名）

| 源 | 产物 | 发生了什么 |
|---|---|---|
| `android.jpg` 6528×3680 | **1916×1080** | 短边 3680 → 1080，长边按比例；4.8 MB → 232 KB |
| `rot.jpg` 3024×4032（竖） | **1080×1440** | 短边同样是 3024 → 1080；产物 `Orientation=1`，朝向已烘焙进像素 |
| `tall.png` 750×30000 | **750×30000（原样不缩）** | 短边 750 已低于上限，一个像素都不动 |

最后一行是短边规则存在的全部理由：**按长边限制会把这张 30000 px 的长截图压成 27 px 宽的
一条线**。（它 128,184 B → **840 B** 的压缩率来自 AVIF 对大片平坦区域的编码，与缩放无关，
别把这个数当成「缩放省了 99%」的证据。）

### 耗时

| | run 1 | run 2 |
|---|---|---|
| 墙钟（20 个文件 / 109.2 MB） | **29 s** | 30 s |
| CPU 时间合计 | 78.6 s | 82.2 s |
| 并行加速比 | **2.8×** | 2.7× |
| CPU 峰值（10 核机） | **803%** | — |

吞吐 **≈ 3.8 MB/s ≈ 0.23 GB/min**。

**关键路径是视频那条队列，被数字直接钉死**：4 个视频合计 58.6 s CPU，视频闸门宽度 2，
58.6 / 2 ≈ 29 s ≈ 整个任务的墙钟。图片和音频那 20 s CPU 全部藏在视频的影子里跑完了——
「双队列耗时取 max」这个预估模型在真机上成立，不是纸面推导。

> **加速比只有 2.8× 不是调度器的问题**。20 个文件里只有 4 个是重活，轻活那条队列
> （闸门 8）在头 2 秒就把 13 张图 + 3 个音频吃完了，剩下 27 秒整台机器只有 2 个 x265 在跑。
> 加速比是被语料构成压下来的——真实归档盘上图片占绝大多数，形状是反过来的
> （十万文件压测里 CPU 是 907%）。

### 内存

| | |
|---|---|
| 空载 | 26~27 MB |
| **峰值** | **765 MB**，出现在开跑后头 ~2 秒 |
| 峰值之后的稳态 | **68 MB**（后续 27 秒一直贴着这个数） |
| ffmpeg 子进程合计峰值 | ~1.4 GB（4 个并发时） |

**曲线的形状比峰值本身重要**：765 MB 是一根 2 秒的尖峰，之后立刻掉回 68 MB 保持到结束。
根因量得出来——轻活闸门 `ncpu-2` = 8，即最多 8 张图同时解码，而语料里最大的 8 张图解成
RGBA8 之后合计 **456.5 MiB**（`android.jpg` 6528×3680 = 91.6 MiB，`tall.png` 750×30000 =
85.8 MiB，另有六张 4032×3024 各 46.5 MiB），再乘约 1.7 倍（缩放目标缓冲 + libavif 的
YUV 平面 + 编码器状态）≈ 765 MB，对得上。

**要紧的安全性质在这里：峰值由闸门宽度决定，不由队列长度决定。** 十万文件跑下来峰值
不会更高——十万文件压测实测中位 167 MB / 峰值 566 MB，比这轮还低，因为那批语料单图分辨率小。

### 确定性

同一份语料、同一套默认参数，两遍跑出来：**20 个条目的 `dst_size` 逐字节相同**，
`diff -rq` 两棵输出树完全一致，扫描报告的预估数字也一模一样。

这条不在三轴里，但它是「基准可复现」的前提——如果同一份输入两次跑出不同产物，
上面所有数字都失去意义。

## 结果 · 基准 21（十万文件规模压测）

语料用 `pnpm bench:100k` 造：`cp -c`（APFS 写时复制）把 `fixtures/` 里的真实素材克隆成
**100,000 个文件、1,137 个目录**，**表观 77.2 GB、实占约 10 MB**，二十秒造完。
克隆出来的是**真文件**——ffprobe 探得到、编码器解得开，与 `truncate` 造的空壳完全不是一回事。

| 项目 | 结果 | 备注 |
|---|---|---|
| **扫描** | **34.11 s / 100,000 文件** ≈ 2,900 文件/秒 | 含 5,000 次视频 + 2,000 次音频 ffprobe 探测 |
| **DB 体积** | **22.7 MiB / 99,000 条** ≈ 240 B/条 | 三个索引合计 12.0 MB，**反超表数据的 9.2 MB** |
| **主进程内存** | 中位 **167 MB**、峰值 566 MB | 按时间四等分，各段中位数 175 / 161 / 153 / 180 MB——**不单调上升** |
| **UI 查询（满载下）** | 深翻页 **2.83 ms** 中位 / 5.33 ms 最差 | 此时 CPU 907%、load average 266 |
| **崩溃恢复** | **202 ms** | `kill -9` 留下 84 条 running + 10 个孤儿临时文件，全部收拾干净 |

**索引比数据还大**这件事记在这里是为了防止后来有人再加索引：两个索引都带 `src_path`
（或以 id 收尾的组合列），而路径是这张表里最长的字段。本轮语料路径平均只有 45 字符，
真实归档盘会长得多——按 120 字符估，十万文件的库大约 45~55 MB。这张表是**写重读轻**
（一次灌十万行，之后每 2 秒读一页），每加一个索引都要在灌库那 34 秒里付账。

## 量错过的地方

这一节比上面的数字更值钱：每一条都是「先量出一个看起来完全合理的数，而它是错的」。

### 内存：`ps -o rss` 会虚报 15 倍

第一版采样脚本用 `ps -o rss`，报出来主进程 **2,270 MB 且一路上涨**——就此收工的话，
结论会是「十万文件下内存涨到 2.2 GB，有泄漏」。`vmmap -summary` 当场推翻了它：
`Physical footprint 149.5M`、`TOTAL DIRTY 156.8M` 而 `RESIDENT 2.0G`。
**libmalloc 释放后把页留在原地不还给内核**，rss 把这些「已经不用、但还没归还」的干净页
全部计入。判据换成 `/usr/bin/footprint -p`——那正是活动监视器「内存」列和 jetsam 用的数。

### 内存：`footprint` 的单位是变的

小进程打 `KB`、大一点打 `MB`、再大打 `GB`。采样器只取数字当 MB 累加，会把 `7889 KB`
读成 7889 MB——**而那看起来完全像一次真实的内存爆炸**。验法一句话：新起一个 `sleep 30`，
`footprint` 报的是 `801 KB`。**凡是解析系统工具输出的地方，先确认单位是不是固定的。**

### 内存：轮询会漏掉最该量到的那一段

每秒轮询量到主进程峰值 306 MB，而 `phys_footprint_peak` 是 **765 MB**。
差的那 459 MB 是一根宽度不到 2 秒的尖峰——**恰好是最该被量到的那一段**。
`phys_footprint_peak` 是 macOS 自己记的全生命周期高水位，不受采样间隔影响。

### 磁盘：`du` 量不出 APFS 克隆省了多少

造十万文件的语料时想确认 clonefile 真的生效了，`du` 会告诉你**一个字节都没省**：
克隆共享数据块，但 `stat` 仍按整份大小报，于是 du 把克隆当成真拷贝。
实测 456 MB（表观）的语料，`du` 报 456 MB，而 `df` 前后差只有 **12 KB**。
**要量实占磁盘只能用 `df` 前后差。**

### ffprobe 给的数字有四种错法

四个都长成同一个形状：**ffprobe 给了一个看起来完全合理的数字，而那个数字是错的**。

| 现象 | 真相 |
|---|---|
| 一张 4032×3024 的 HEIC 报成 **512×512** | 它挑中了 HEIF 容器里的**缩略图 item**。图片规格一律走 ImageIO |
| 动画 AVIF 报 **1 帧** | ffmpeg **不会迭代 AVIF 图像序列**。ImageIO 报 10 帧、类型 `public.avis`——**产物是对的，是探测工具不行**。差点当成「动图管线只写了首帧」去查 |
| 源容器 `nb_frames` = **526**，实际 **436** | 容器里那个数就是源文件自己写错的。`-count_frames` 一数就对上。差点当成掉帧 bug |
| CMYK JPEG 的渲染 | 这一次反过来，**ffmpeg 对、ImageIO 错**（见下） |

**通用做法**：拿 ffprobe 的读数下「管线有 bug」这种结论之前，先用第二个工具复核一遍。
本轮有两次差点写出错误的 bug 报告，两次都是复核救回来的。

### 参考解码器：ImageIO 和 ffmpeg 各错一次

质量轴要一个「真值」解码器，默认选 ImageIO（应用自己走的就是它）。本轮破例两次：

- **`cmyk.jpg` 是 Adobe 反相 CMYK JPEG**（带 APP14 段、`transform=0`、无 ICC）。
  **ImageIO 把它渲染成反相的**（青红互换），ffmpeg 渲染正确。用 ImageIO 当参考会得到
  **-64 分**的假分——而产物本身是对的（管线内部这条路没走 ImageIO）。换 ffmpeg 后 **87.89**。
- **动画 AVIF 的首帧，ImageIO 的 index 0 取出来不对**。同一张 `anim.gif` 的产物，
  ImageIO 解产物端得 **-4.81**，ffmpeg 解得 **75.51**——两端一起换 ffmpeg 才对得上。

两条合起来的结论：**没有哪个解码器总是对的**。看到一个离谱的低分，先怀疑解码器，
再怀疑管线。

### shell 里两个会静默算错的坑

- awk 处理带 `#` 表头的日志要先 `/^#/{next}`，否则表头那行的字符串会把 `$2 > max`
  整个变成**字符串比较**，峰值全部算成 0。
- `set -- $pair` 在函数外的 while 循环里不做词分割，要么换 `read`，要么老实用两个变量。

### 要复现「首次运行」的系统授权行为，先 `tccutil reset`

本机一旦授权过，任何与 TCC 相关的路径（自动化 / 完全磁盘访问 / 文件夹权限）都测不出
真实的首次体验，**而用户遇到的恰恰是首次那一次**。本轮用的是
`tccutil reset AppleEvents com.zigzag.app`；验完再查一遍 `TCC.db` 的
`where client like '%zigzag%'`——**零行**才说明真的没申请过，而不是「弹了但我没注意到」。

> 这条不是闲话。它是本轮抓出 v1 最后一个阻断级 bug 的方法：查重的删除路径绕过了平台
> 包装层，会弹出「控制访达」的授权请求，**用户一旦点「不允许」，删除功能就永久失效**，
> 而失效的表现是「点了确认但文件还在」。单测测不到它——本机授权过一次就再也不弹，
> 测试环境里它表现得和正确实现一模一样。详见 [PROGRESS.md · ADR-021 §17.7](../PROGRESS.md)。

## 这份语料回答不了什么

写在最后，免得数字被拿去过度解读：

- **整体压缩率不是有代表性的加权平均**。视频占了 75% 的字节，而真实归档盘上照片才是主力。
  能对外说的是分 kind 那三个数。
- **没有「已压实的 AVIF/WebP」样本**，所以无收益跳过一次都没触发——而那在真实归档盘上
  是常态路径。
- **耗时门槛在小语料上近乎恒真**。预估报「不到 1 分钟」，实测 29 s，落在区间内；
  可是区间的显示粒度是分钟，29 秒的任务无论如何都会落进去。要真正压这条门槛，
  得拿一个跑够十几分钟的语料再来一次。
- 跑 `pnpm bench:image` 会看到 `plain.jpg` 被跳过——它的产物在查重走查里被移进废纸篓了，
  这是预期内的。
