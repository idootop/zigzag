# ZigZag

**体积更小，画质如初**

面向本地归档的多媒体批量压缩工具。<br/>
在肉眼无损的前提下，把照片压到约 **1/10**、视频压到约 **1/5**<br/>

## 它解决什么问题

移动硬盘里归档的照片和视频，多数出自早期设备，用的是今天看来效率偏低的编码格式，
白白占着大量本可以释放的空间。而现成的批量压缩方案往往在三件事上让人不放心：
处理慢、画质损失不可控、任务断了就得从头再来。更要命的是，多数工具压完就覆写或删除原文件，
一旦出错便无从挽回。

ZigZag 想让归档整理变成一件**可预期、可中断、可回滚**的事：
选好目录，先看预估能省多少，确认后再开始，随时可以关机，下次打开接着跑。

## 特性

**压得下去，也看得清楚**

- **三条独立管线** — 图片、视频、音频各走各的路，编码参数都经过基准测试验证
- **短边约束缩放** — 以短边为基准做统一缩放，长截图、竖拍照片、全景图都能正确处理，
  不会像按长边限制的工具那样把长截图压成一条线
- **动图一并处理** — GIF / APNG / 动画 WebP 转为动画 AVIF，实测省 45%~87%
- **压缩前后对比** — 拖动分界线左右对照画面，下方并排列出体积、分辨率、编码格式与码率；
  视频两侧截取同一时刻，音频直接看码率变化

**元数据原样保留**

归档的价值一半在像素，一半在这些信息上——压缩不该把它们弄丢：

- **拍摄时间、地点、设备与镜头参数全部保留** — EXIF 语义段（含 GPS 与厂商 MakerNote）
  与 XMP 原样照搬，只剥掉内嵌的缩略图；视频与音频同样带走容器里的拍摄信息
- **ICC 色彩描述始终保留** — 它决定像素怎么被解释，丢了整张图会偏色，因此不受任何开关影响
- **文件日期跟着走** — 产物继承源文件的创建与修改时间。这一条容易被忽略却很致命：
  macOS 的 Spotlight 并不从 AVIF 里读 EXIF，在访达和「照片」里，**唯一存在的日期就是文件日期**，
  不搬的话一块二十年的归档盘会整个塌缩成压缩当天
- 不想留这些信息的话，图片可以在设置里关掉「保留拍摄参数」，整份 EXIF / XMP 都不写入
  （ICC 与文件日期不受影响）

**跑得稳，也不怕断**

- **先扫描，后处理** — 执行前给出体积分布、预计节省空间与预计耗时，确认后再开始
- **断点续传** — 进度落在 SQLite 里，异常退出或主动停止后重新打开，界面直接摆出上次的
  进度和一个「接着跑」，输出目录不必再选一遍（十万文件实测：恢复耗时 202 毫秒）
- **跳过无收益的文件** — 自动识别已经压得很实的文件，避免无效处理与二次劣化
- **开跑前先算空间** — 输出盘装不下就当场拦住，并直接告诉你需要多少、还剩多少
- **说清哪些东西不会被复制** — 输出目录只放媒体文件，报告里会点名文档、`.xmp` / `.aae`
  编辑记录与照片图库包各有多少个。打算用输出目录替换源目录的话，你会提前知道要另外备份什么

**顺手清理重复文件**

- **完全相同的** — 三级比对（文件大小 → 采样哈希 → BLAKE3 全量校验），能识别硬链接
- **长得很像的** — 感知哈希找出同一张照片的不同版本（改过尺寸、重新导出、加过滤镜），
  逐组显示相似度，**默认一个都不勾选**，删哪份由你决定
- 删除一律走废纸篓，且必须人工确认

**输出可控**

- 产物文件名支持 `{name}` / `{srcext}` / `{ext}` 三个占位符，设置界面实时预览；
  只改文件名，目录层级始终与源目录一一对应
- `{name}_{srcext}.{ext}` 这样的模板可以把 `IMG_0001.HEIC` 与 `IMG_0001.JPG`
  这类同名不同格式的照片分开

## 实测

发布前验收基准跑的是打包好的 `.app`、默认档，机器为 Apple M1 Max：

| 类型 | 压到原体积 | 约等于 | 质量 |
|---|---|---|---|
| **照片** | 14.3% | **1/7** | SSIMULACRA2 真实照片全部 ≥ 79（90 ≈ 视觉无损） |
| **视频** | 21.3% | **1/5** | VMAF 96.0 ~ 98.8（兜底闸门 80 分） |
| **音频** | 14.3% | **1/7** | 已是 AAC 的源只换容器，逐字节不变 |

同一份输入跑两遍，产物逐字节相同；十万文件压测下内存中位 167 MB 且不随时间上涨。

> 分类型的数字比整体数字更可信——整体压缩率会随语料构成漂移，分类型的不会。
> 你自己的盘上能省多少，扫描阶段会先给一个区间。
> **测试方法、完整数据与可复现脚本见 [bench/README.md](bench/README.md)。**

## 快速上手

暂未提供安装包，需要自行构建。前置条件：Node.js + [pnpm](https://pnpm.io)、
[Rust 工具链](https://rustup.rs)。

```bash
pnpm install
pnpm sidecars        # 下载随包的 ffmpeg / ffprobe（约 130 MB，不进 git）

pnpm tauri dev       # 开发模式运行
pnpm tauri build     # 打包出 .app 与 .dmg
```

打包产物在 `src-tauri/target/release/bundle/` 下。

> [!IMPORTANT]
> **首次打开需要手动放行。** 本项目不上架 App Store、也不做 Apple 公证，
> 安装包采用本地自签名，因此 macOS 会提示「Apple 无法验证……是否包含恶意软件」。
> macOS 15 起那个对话框上**已经没有「打开」按钮**，早年流传的「右键 → 打开」不再有效。
> 放行方式二选一：
>
> - 前往**系统设置 → 隐私与安全性**，在底部点击「仍要打开」；
> - 或在终端执行 `xattr -dr com.apple.quarantine /Applications/ZigZag.app`。
>
> 只需操作一次，之后正常双击即可。

## 系统要求

**macOS · Apple Silicon。** 项目目标平台就是它，暂不考虑适配 Intel Mac、Windows 或 Linux。

这不是随口一句：应用把 macOS 专有能力用到了实处——ImageIO 承担疑难格式的解码兜底、
VideoToolbox 提供硬件编码、QuickLook 出缩略图、APFS `clonefile` 让无收益文件零拷贝落地。
不过平台相关代码全部收拢在 `src-tauri/src/platform/` 一个目录里，与核心逻辑解耦，
**需要移植的话自行扩展即可**，不必重构。

## 默认策略

| 类型 | 目标格式 | 关键参数 |
|---|---|---|
| **图片** | AVIF | 短边上限 1080、质量 85、4:4:4 色度；一律有损；元数据与 ICC 保留，朝向烘焙进像素 |
| **视频** | HEVC（x265） | 短边上限 1080、帧率上限 30、CRF 24、8-bit；默认软编，硬件编码作为「极速」预设可选 |
| **音频** | AAC-LC（`.m4a`） | 码率上限 128 kbps，继承源采样率；AAC 源仅更换容器，不重新编码 |

两道落地闸门也有默认值：**产物至少要省下 20%**（省得比这少就保留原文件——
改写一个归档文件本身是有代价的），**视频产物 VMAF 低于 80 分直接丢弃**
（这是兜底线而非画质目标，默认参数实测在 96 分以上）。

以上参数均可调整，并提供三档预设（省空间 / 均衡 / 极致画质）与折叠式高级设置。
默认路径无需任何配置。

## 数据安全

| | 原则 | 说明 |
|---|---|---|
| **P1** | 数据安全优先 | 原文件在产物通过完整性校验前不会被删除或覆写。宁可不压缩，不可压坏 |
| **P2** | 压缩率不妥协 | 任何以体积换速度的选择都需有明确依据，默认档不牺牲压缩率 |
| **P3** | 可中断、可恢复 | 十万级文件的任务可随时中止并恢复，每个文件的处理结果均有记录可查 |

默认输出至镜像目录，原文件保持不变，**回滚操作就是删除输出目录**。
原地替换需要显式开启，且删除一律经过废纸篓。

## 技术栈

- **前端** — React 19、Vite、TypeScript、Tailwind 4、shadcn/ui、TanStack Virtual
- **后端** — Rust、tokio、rusqlite（WAL 模式）、image、fast_image_resize、libavif
- **编解码** — ffmpeg / ffprobe sidecar，叠加 macOS 的 ImageIO 与 VideoToolbox

空载内存约 26 MB，跑动时稳态约 68 MB。大规模目录遍历与哈希计算走
`jwalk` + `rayon` + `blake3`。安装包约 65 MB，其中自身二进制只有 18 MB，
其余几乎全是随包携带的 ffmpeg 与 ffprobe——这两个静态构建刻意没有裁剪，
因为归档盘上真正需要它们的，恰恰是那些冷门的早期编码格式。
